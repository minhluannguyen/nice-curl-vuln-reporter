# CURL security report summary

This page provides an overview of curl vulnerability reproduced using NICE curl vulnerability reporter. Each report includes a detailed description of the vulnerability, the affected curl versions, VM configurations, testable reproduction steps, and related artifacts.

### Summary of reports

| CVE ID | Description | Affected Versions | Test description | Note | 
|--------|-------------|-------------------|------------------|------|
| [CVE-2022-27778](https://curl.se/docs/CVE-2022-27778.html) | A use of incorrectly resolved name vulnerability fixed in 7.83.1 might remove the wrong file when `--no-clobber` is used together with `--remove-on-error`. | 7.83.0 | A client's important file is overwritten after connecting to a malicious server. The test ensures the file exists before the connection and was replaced after the connection. | |
| [CVE-2022-32206](https://curl.se/docs/CVE-2022-32206.html) | curl < 7.84.0 supports "chained" HTTP compression algorithms, meaning that a serverresponse can be compressed multiple times and potentially with different algorithms. The number of acceptable "links" in this "decompression chain" was unbounded, allowing a malicious server to insert a virtually unlimited number of compression steps.The use of such a decompression chain could result in a "malloc bomb", makingcurl end up spending enormous amounts of allocated heap memory, or trying toand returning out of memory errors. | 7.57.0 to and including 7.83.1 | Check if the client's memory usage exceeds a certain threshold after connecting to a malicious server that sends a response with a long decompression chain. | |
| [CVE-2022-35260](https://curl.se/docs/CVE-2022-35260.html) | curl can be told to parse a `.netrc` file for credentials. If that file endsin a line with 4095 consecutive non-white space letters and no newline, curlwould first read past the end of the stack-based buffer, and if the readworks, write a zero byte beyond its boundary.This will in most cases cause a segfault or similar, but circumstances might also cause different outcomes.If a malicious user can provide a custom netrc file to an application or otherwise affect its contents, this flaw could be used as denial-of-service. | 7.84.0, 7.85.0 | Check for segmentation fault when curl is configured to use a `.netrc` file with a long line of non-white space characters. | |
| [CVE-2023-23915](https://curl.se/docs/CVE-2023-23915.html) | A cleartext transmission of sensitive information vulnerability exists in curl <v7.88.0 that could cause HSTS functionality to behave incorrectly when multiple URLs are requested in parallel. | 7.77.0 to and including 7.87.0 | A network topology with 2 seperate networks is set up, where a client can access three other servers through a router. The client sends parallel requests with HSTS cache to three servers, it then sends another request to server1 with confidential content. The router will intercept the request and check if the confidential content is sent in cleartext. | The parallel requests is non-deterministic, so the test is set to retry a few times |
| [CVE-2023-28321](https://curl.se/docs/CVE-2023-28321.html) | An improper certificate validation vulnerability exists in curl <v8.1.0 in the way it supports matching of wildcard patterns when listed as "Subject Alternative Name" in TLS server certificates. curl can be built to use its own name matching function for TLS rather than one provided by a TLS library. This private wildcard matching function would match IDN (International Domain Name) hosts incorrectly and could as a result accept patterns that otherwise should mismatch. | 7.12.0 to and including 8.0.1 | A client connects to a IDN server with a certificate containing a wildcard pattern that should not match the server's hostname. The test checks if the connection is successful to confirm the vulnerability. | The artifact (certificate) for this case is not reproducible, in the future, it should be generated as part of the test setup. |
| [CVE-2023-38039](https://curl.se/docs/CVE-2023-38039.html) | When curl retrieves an HTTP response, it stores the incoming headers so that they can be accessed later via the libcurl headers API. However, curl did not have a limit in how many or how large headers it would accept in a response, allowing a malicious server to stream an endless series of headers and eventually cause curl to run out of heap memory. | 7.84.0 to and including 8.2.1 | The test checks if the client's memory usage exceeds a certain threshold after connecting to a malicious server that repeatedly sends large headers. | |
| [CVE-2023-38545](https://curl.se/docs/CVE-2023-38545.html) | This flaw makes curl overflow a heap based buffer in the SOCKS5 proxy handshake. When curl is asked to pass along the host name to the SOCKS5 proxy to allow that to resolve the address instead of it getting done by curl itself, the maximum length that host name can be is 255 bytes. If the host name is detected to be longer, curl switches to local name resolving and instead passes on the resolved address only. | 7.69.0 to and including 8.3.0 | The test makes sure the proxy server is up before the client connects, then checks for a core dump after the connection. | There is another version for this case that use the curl that is built from source (not from nixpkgs). This report is also required custom nix configurations to set up the SOCK5 proxy. |
| [CVE-2025-5399](https://curl.se/docs/CVE-2025-5399.html) | Due to a mistake in libcurl's WebSocket code, a malicious server can send a particularly crafted packet which makes libcurl get trapped in an endless busy-loop. | 8.13.0, 8.14.0 | The test checks if the client's cpu usage exceeds a certain threshold after connecting to a malicious server that sends a crafted WebSocket packet. | |
| [CVE-2026-4873](https://curl.se/docs/CVE-2026-4873.html) | A vulnerability exists where a connection requiring TLS incorrectly reuses an existing unencrypted connection from the same connection pool. If an initial transfer is made in clear-text (via IMAP, SMTP, or POP3), a subsequent request to that same host bypasses the TLS requirement and instead transmit data unencrypted. | 7.20.0 to and including 8.19.0 | The client first sends a control case where the connection is an IMAP request that requires TLS, but the server does not support it, thus the connection fails. Then the client sends a reuse case but this time with a second transfer that does requires TLS, this time it succeeds. The assertion checks if the connection did attempt STARTTLS or not (it should). | |
